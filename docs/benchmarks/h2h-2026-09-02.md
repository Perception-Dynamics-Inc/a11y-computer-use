# cu-arena head-to-head, 2026-09-02

Same planner, same tasks, three loops. The refs loop completed every task; the
screenshot-and-coordinates loop completed about half; adding snap-to-ref to the
coordinate loop did not help in this run. Read the caveats before quoting a number:
this is one round of one planner on plain fixtures in headless Chrome, and the
harness found and fixed two of our own bugs along the way (they are listed below,
with the results before and after).

## What the rows say

- Where the pixel loop succeeded it usually needed two to four times the turns:
  a field takes a click and then a type, where the refs loop calls `set_value`
  once, and after every action the pixel loop reads a new screenshot.
- The pixel loop matched the refs loop on `similar_buttons` (two turns each) and
  `table_row` (three turns against two), and it beat the refs loop on
  `search_filter`: five turns against seven, zero misclicks in both. The refs
  planner spent two extra turns re-observing after the filter changed the list.
  That is a real result against the thesis and it stays in the table.
- Every pixel failure has the same shape in the recorded clicks: a coordinate 10
  to 30 px below the intended control (a button spanning y 519 to 559 clicked at
  y 567; a toggle spanning y 100 to 138 clicked at y 145), followed by the same
  coordinate repeated after the screenshot showed no change. The misclick column
  counts those clicks, which the fixture recorded as hitting `body`. Whether that
  is the model's coordinate estimate or something about how the CLI presents the
  image to it was not diagnosed here; the screenshot files are 1280x713 and the
  page coordinates are 1:1 with them.
- `pixels+snap` did not beat `pixels` in this run (6 against 7 completed, more
  misclicks). Snap-to-ref can only help a click that already lands inside an
  actionable element; the clicks that missed had nothing under them to snap to.
  Where the coordinate was right the snap executed the click as a ref press
  (`long_list`, `similar_buttons`, `table_row`). One round cannot separate that
  from noise.
- The refs loop's cost advantage is mostly turns, not tokens per turn: a refs
  turn cost about 16 to 25k input tokens here (the CLI's prompt plus a 600 to
  4,000 character snapshot), a pixel turn about 13 to 15k plus the image read,
  but the pixel loop took twice the turns and hit its budget on six tasks.

## Bugs the harness found in our own code

Three problems surfaced during the run. All three are fixed in the same branch,
with tests, and the affected tasks were rerun; the superseded rows are kept in
`h2h-2026-09-02-superseded.json`.

1. Browser wheel scroll had the wrong sign. `drivers/browser.py` negated `dy`
   the way the macOS driver does, but CDP uses the tool contract's sign already,
   so every "scroll down" was a scroll up and, at the top of a list, a no-op. All
   three modes failed `long_list` for this reason in the first run (refs 0/1 in
   10 turns, pixels 0/1, pixels+snap 0/1). With only the sign fixed, an
   intermediate rerun gave refs 1/1 in 10 turns (manual scrolling), pixels 1/1 in
   4, pixels+snap 1/1 in 5.
2. `scroll_to_find` wheeled over the window, not the list. Its anchor preferred
   `AXScrollArea` and then fell back to the largest element; the browser backend
   exposes an overflow `<ul>` as `AXList`, so the wheel landed on the page. The
   anchor now prefers list, table and outline containers smaller than the window,
   and the tool takes an optional `ref`. With both fixes the final `long_list`
   rows above are refs 3 turns, pixels 4, pixels+snap 6.
3. The confirmation gate blocked only the refs loop. A ref click on a button
   titled "Delete" trips the Runtime's irreversible-action classifier; a raw
   coordinate click carries no title and does not. In the first run the refs
   planner was refused on `modal_confirm` (`confirmation_declined`) and gave up
   correctly, while the pixel loops ran unhindered. The harness now hands the
   same approving callback to both loops. Final rows: refs 3 turns, pixel modes
   still 0/1 for planner reasons (6 and 5 misclicks).

The `wasted` definition also changed once during the day: the first run counted a
click that only focused a field as wasted, which penalised the pixel loop for a
step it cannot skip. Focus is part of the state digest now; the whole suite was
rerun after that change, so every row above uses the same definition.

## Caveats

- One round per task per mode. A single cell is a single sample; `--rounds`
  exists for a reason.
- One planner, reached through the Claude Code CLI. Token counts include the
  CLI's system prompt on every stateless call, for all modes. Cost is the CLI's
  reported list price, not a bill.
- Plain fixtures, 13 of them, in headless Chrome. Production pages are denser
  and slower; desktop applications are not covered here (see `bench desktop`).
- The turn budget is the same for every mode by design, and the pixel loop needs
  more turns for the same task by construction. Six of its failures are budget
  exhaustion, not a wrong final state.
- `dropdown` is flagged as not comparable for the pixel modes and excluded from
  the comparable-tasks rate; the aggregate shows both rates.
- The result set is assembled from four invocations (below), not one. Every
  invocation used the same planner, model, browser build and machine on the same
  day.

## How this result set was assembled

1. `computeruse bench h2h --provider claude-cli --rounds 1` over the 12 original
   tasks (run 2 of the day, after the focus-aware digest). All rows except
   `long_list` and `modal_confirm` come from it.
2. `--tasks modal_confirm` after the confirmation-gate fix.
3. `--tasks long_list` after the wheel-sign and scroll-anchor fixes.
4. `--tasks dropdown_custom` (the task was added after the dropdown popup issue
   was understood).

The four `h2h.json` files were merged and rendered with
`computeruse bench h2h --render ... --out`, which applies the manifests'
comparability notes and computes the with/without rates.
